Шаг 1. Сравнение Colab и Marimo

Традиционные ноутбуки (Colab) имеют три ключевых ограничения для MLOps.
Первое – проблема скрытого состояния. В Colab ячейки можно запускать в любом порядке. Например, можно изменить переменную в первой ячейке, не перезапустив последнюю, и получить неверный результат. Marimo решает это через реактивность – любое изменение в коде мгновенно обновляет все зависимые ячейки, что гарантирует воспроизводимость эксперимента.
Второе – формат файлов. Файл Colab (.ipynb) – это запутанный JSON с метаданными и служебной информацией. При сравнении двух версий такого файла в Git трудно понять, что именно изменилось в коде. Marimo сохраняется в обычный .py файл – можно видеть только свой код, без лишнего “мусора”. Это критически важно для командной разработки.
Третье – готовность к продакшену. Код из Marimo – это уже готовый Python-скрипт. Его можно сразу запустить на сервере, обернуть в Docker или встроить в автоматический пайплайн без переписывания. Colab для этого не предназначен.
Таким образом, Colab хорош для быстрого прототипирования, но для промышленных ML-проектов Marimo – более правильный выбор.

Шаг 2. Обеспечение воспроизводимости (DVC/MLflow)

В рамках данного этапа была построена архитектура воспроизводимого машинного обучения, решающая проблему «непрозрачных» экспериментов. 
Реализовано разделение хранения кода и данных. Исходный датасет был вынесен под контроль DVC, что позволило исключить хранение тяжелых бинарных файлов в Git. Теперь Git отслеживает только метафайлы (.dvc), гарантируя связь конкретной версии кода с версией данных.
С помощью файла dvc.yaml был сконфигурирован конвейер, состоящий из стадий prepare (подготовка и сплит) и train (обучение). Это обеспечило автоматизацию: команда dvc repro самостоятельно отслеживает изменения и перезапускает только необходимые этапы.
Все ключевые параметры вынесены в файл params.yaml. Это позволяет изменять конфигурацию эксперимента без вмешательства в исходный код скриптов.
В проект интегрирована система трекинга MLflow. Все параметры и метрики качества (accuracy) автоматически записываются в локальную базу данных (mlflow.db). Это обеспечивает сохранность результатов каждого эксперимента и позволяет проводить аудит обученных моделей.

Шаг 3. Хранилище признаков (Feature Store)

В рамках данного этапа в архитектуру проекта был внедрен инструмент Feast, выполняющий роль централизованного хранилища признаков (Feature Store). 
Для обеспечения масштабируемости системы был использован шаблон PostgreSQL. Файл конфигурации feature_store.yaml успешно прошел валидацию, подтвердив готовность системы к работе с внешними базами данных. В ходе работы был развернут и настроен Docker-контейнер с PostgreSQL (feast-postgres), что позволило протестировать онлайн-хранилище в условиях, максимально приближенных к реальному продакшену. С помощью команды feast apply была успешно развернута инфраструктура признаков. Успешно запущен сервис feast serve, предоставляющий рабочий эндпоинт на порту 8080. Это позволяет внешним сервисам получать признаки (features) в реальном времени через стандартизированный API.

Шаг 4. Обоснование готовности ML-системы к развертыванию

Промышленная ML-система (в отличие от обычного скрипта) включает в себя:
-  Сбор и версионирование данных (DVC): Отслеживание изменений в датасетах.
-  Feature Store (Feast): Централизованное хранилище признаков для обучения и инференса.
-  Эксперимент-менеджмент (MLflow): Логирование каждой итерации обучения.
-  Model Registry: Хранилище версий моделей, готовых к эксплуатации.
- Serving Layer (API): Сервис (например, FastAPI), который принимает данные и отдает предсказания.
-  Мониторинг: Отслеживание качества модели и «дрифта» (сдвига) данных в реальном времени.
-  CI/CD пайплайны: Автоматические тесты кода и моделей перед выпуском.

Для текущего проекта (детекция и размытие лиц):
-  DVC и MLflow – необходимы, так как работа ведется с изображениями и видеоданными и важно знать, на каких данных и с какими параметрами обучена модель.
-  Feature Store – полезен, если мы будем использовать дополнительные признаки (например, метаданные о времени или месте съемки) для улучшения точности.
-  Мониторинг и API - критичны, если мы хотим встроить размытие лиц в реальный видеопоток (например, на камерах видеонаблюдения), чтобы вовремя заметить, если модель перестала узнавать лица при плохом освещении.

Система не готова к полноценному развертыванию.
Хотя наличие репозитория и блокнота – хороший старт, этого недостаточно по следующим причинам:
1.	Проблема «скрытого состояния»: Блокноты (особенно Colab) зависят от порядка запуска ячеек и временной среды. Это нарушает принцип воспроизводимости.
2.	Отсутствие инференс-сервиса: Блокнот нельзя вызвать как API-функцию из другого приложения.
3.	Нет гарантии стабильности: Блокнот не обеспечивает автоматическую проверку ошибок (тестирование) и не предназначен для высоких нагрузок.
4.	Отсутствие мониторинга: Мы не узнаем, если в реальных условиях точность модели упадет.

Таким образом, текущий проект является качественным MVP (минимально жизнеспособным продуктом). Благодаря DVC, MLflow и Feast был заложен фундамент, но для «продакшена» систему необходимо упаковать в микросервис (через созданный Dockerfile) и настроить мониторинг.

Схематическое описание (Architecture)
Для промышленного использования предлагается архитектура, разделенная на независимые слои:
1.  Слой данных (Storage Layer): Видеофайлы и веса моделей классификатора (Haar Cascades) версионируются с помощью DVC.
2.  Слой параллельных вычислений (Processing Layer):
   -  Видео разбивается на независимые фрагменты (чанги).
-  Несколько Worker-узлов (Docker-контейнеры) одновременно обрабатывают фрагменты, используя библиотеку OpenCV.
3. Слой признаков (Feature Layer): С помощью Feast подтягиваются актуальные параметры анонимизации (например, pixel_size для разного качества видео).
4. Слой мониторинга (Tracking Layer): MLflow фиксирует метрики производительности                            и метаданные каждого запуска.
Данная схема позволяет масштабировать обработку видео пропорционально количеству доступных вычислительных ресурсов. Параллелизм на уровне данных сокращает время анонимизации в несколько раз, что критически важно для соблюдения юридических норм защиты персональных данных.
